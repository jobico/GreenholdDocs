The last page of the setup wizard shows the command line for the agent installer.
It uses the values of your server.

## 1. Install the agent

On the agent computer, open an elevated prompt.
Run the command that the wizard made:

```
msiexec /i C:\path\Greenhold-Agent-<version>-x64.msi /qn /norestart LICENSEACCEPTED=1 POLICYENROLLMENTURL="https://<name>:8444" POLICYCHANNELURL="https://<name>:8443" POLICYCHANNELAUTHORITY="<base64 DER of channel-authority.cer>" POLICYINSTALLATIONROOT="<policy value of root.public.json>" POLICYINSTALLATIONID="<installation id>" /l*v greenhold-agent-install.log
```

These are the POLICY values:

| Property | Value |
|---|---|
| `POLICYENROLLMENTURL` | `https://<gateway name>:8444` |
| `POLICYCHANNELURL` | `https://<gateway name>:8443` |
| `POLICYCHANNELAUTHORITY` | The gateway authority certificate, as base64 DER |
| `POLICYINSTALLATIONROOT` | The policy value of `root.public.json` |
| `POLICYINSTALLATIONID` | `installationId` from `root.public.json` |

:::caution[A software key needs one more property]
An agent accepts only hardware-backed keys by default: Windows Hello, passkey, security key and vault.
It refuses an Order that is signed with a software key.
A key file of Greenhold Admin and the key that the setup wizard makes on the server are software keys.
For a lab, add this property to the command:

```
POLICYACCEPTEDKEYKINDS="software,windows-hello,passkey,security-key,vault"
```

The value replaces the whole list. It does not add to the defaults.
Give every kind that you accept.
In version 0.1.4, a TPM key is `windows-hello`.
With `software` alone, the agent refuses an Order that a TPM key signed.

The wizard adds it when you tick **My administrator's key is a software key (a lab)**.
Do not use software keys in production.
See [Strict defaults](/concepts/policy-for-agents/#strict-defaults).
:::

The installer starts the agent only when you add `STARTSERVICES=1` to the command.
Otherwise, start it after the install:

```powershell
Start-Service GreenholdAgent
```

To get the authority certificate as base64, run this on the server:

```powershell
[Convert]::ToBase64String([IO.File]::ReadAllBytes('C:\ProgramData\Greenhold\Gateway\channel-authority.cer'))
```

For many computers, deliver the same values with Group Policy or Intune.

:::note
Never put an enrollment token on a command line.
Every process on the computer can see a command line.
:::

## 2. Make a token

A token lets one device enroll one time.
It lasts at most 7 days.

<Tabs syncKey="interface">
<TabItem label="GUI">

1. In the Manager, open **Add devices**.
2. Choose **One token for each name in a list**. Type the name of the computer, for example `PC-01`.
3. In **The tokens expire after**, choose a time, for example **1 day**.
4. Choose **Make the tokens and download the file**.

You get a CSV file with the columns `name`, `token` and `expires`.
For many devices, see [Add devices](/manager/add-devices/).

</TabItem>
<TabItem label="CLI">

On the server, open an elevated PowerShell:

```powershell
cd "C:\Program Files\Greenhold\Gateway"
.\Greenhold.Gateway.exe token new --name PC-01 > token.txt
```

`--name` or `--pattern` is required.
Use a pseudonym or the computer name.
The token is shown one time.
Use `--lifetime` to set a shorter life, for example `--lifetime 2:00:00`.

</TabItem>
</Tabs>

## 3. Enroll

On the agent computer, open an elevated PowerShell and run:

```powershell
& "C:\Program Files\Greenhold\Agent\Greenhold.Agent.exe" enroll
```

The agent asks for the token.
Paste it.
The agent does not show the token while you type or paste it.
It prints one line, for example `Enrolled. Device ID: <device id>. Key protection: TPM.`

To enroll from a script, give the token file on standard input.
Move the file over a protected route, and delete it after:

```powershell
Get-Content token.txt | & "C:\Program Files\Greenhold\Agent\Greenhold.Agent.exe" enroll
Remove-Item token.txt
```

:::tip
Never put the token on the command line. `enroll` refuses it.
Do not use `--token-file`.
That option deletes its file after enrollment and can fail when it cannot delete.
:::

If enrollment fails, make a new token.
Each try uses the token.

## 4. Check

<Tabs syncKey="interface">
<TabItem label="GUI">

In the Manager, open **Devices**.
The device shows the state **Enrolled** and, after its first contact, the Session **Connected**.
Choose the device to see its details.

</TabItem>
<TabItem label="CLI">

On the agent computer, in an elevated PowerShell:

```powershell
& 'C:\Program Files\Greenhold\Agent\Greenhold.Agent.exe' status
```

On the server, in an elevated PowerShell:

```powershell
& 'C:\Program Files\Greenhold\Gateway\Greenhold.Gateway.exe' agent list
```

The device appears in both places.
The Manager shows it too.

Look at these lines of the `status` output:

| Line | Use |
|---|---|
| `Device id` | The ID of the device. It has 32 characters. An Order names the device with this ID. Write it down. |
| `Server` | `yes` when the computer runs a server edition of Windows. By default, an Order for a server needs two signers. See [Second signer and tags](/dispatch/second-signer-and-tags/). |
| `Connected` | `yes` when the agent service runs and the gateway answered in the last minutes. When it is `no`, the line says why. The agent tries again by itself. |
| `Last contact` | When the gateway last answered, in the local time of the computer and in UTC. `never` before the first connection. |
| `Agent log` | The path of the agent log, `%ProgramData%\Greenhold\Agent\agent.log`. Read it when the agent is not connected. |

`agent list` shows only the first 8 characters of the device ID.
`agent list --wide` shows the whole ID.

</TabItem>
</Tabs>
